# Этап 3: офлайн-валидация форматов, калибровка и независимое оценивание

**Нормативные источники (только поддерживаемые границы):**
- [RFC 3261](https://www.rfc-editor.org/rfc/rfc3261.html) — SIP start-line, Via/Call-ID/CSeq, Content-Length, разделы 7, 8, 20.
- [RFC 6733](https://www.rfc-editor.org/rfc/rfc6733.html) — Diameter header и AVP length/padding, разделы 3, 4.1.
- [3GPP TS 29.274](https://portal.3gpp.org/Specifications.aspx) — GTPv2-C header, TEID, sequence, IE envelopes, §5 (см. также замороженный справочник `standards/release18.json`).
- [RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html) — девятиоктетный HTTP/2 frame envelope, §4.1.
- Диссертация пользователя: разделы 3.2, 3.4–3.8 и 4.1 — структура синтетической нагрузки, КИЕ, отдельные протокольные детекторы и повторные прогоны. **Программная реализация межпротокольной корреляции в диссертации (§3.6) названа будущей задачей**, а не завершённой частью эксперимента. Реализованная ниже эпизодная оценка — новое дополнение HetNet, не результат диссертации.

Все валидаторы **read-only**, не открывают сокеты и ограничивают размер входа (1 МиБ). Из SIP выдаётся **SHA-256 Call-ID вместо исходного значения**; Diameter AVP payload и SIP body не включаются в JSON-вывод. Тем не менее входной файл может содержать конфиденциальную информацию, а GTP TEID остаётся доступным в результате разбора: используйте только разрешённые и обезличенные записи.

## 1. Поддерживаемый формат и строго обозначенные исключения

| Валидатор | Реализованное подмножество | Не поддерживается |
|---|---|---|
| `sip` | Request/response line, CRLF headers, Via, To, From, Call-ID, CSeq, Content-Length и длина body в байтах | compact headers, folded headers, SDP, SIP digest/AKA, retransmit timers, полный ABNF |
| `diameter` | v1, 20-байтовый header, command code, flags, application/hop/end IDs, AVP boundaries, vendor flag и 4-byte alignment | типы данных/значения AVP, grouped AVP recursion, TLS/SCTP и полноценная S6a грамматика |
| `gtpv2c` | version, T/TEID, message length, sequence number, flat IE envelopes и instance | piggyback, весь каталог и семантика IE, таймеры GTPv2-C, сети передачи |
| `http2` | 9-byte frame header, длина (default MAX_FRAME_SIZE), stream ID, несколько типовых ограничений SETTINGS/PING/WINDOW_UPDATE | dynamic SETTINGS, HPACK, connection/stream FSM, OAuth2/TLS, API 3GPP SBI/OpenAPI |
| ОКС-7 MAP/TCAP | В текущем этапе нет нового wire-парсера | ASN.1 BER, SCCP, MTP, SIGTRAN остаются предметом следующего этапа |

Пример команды с **синтетическим** Diameter-заголовком:

```bash
python -m hetnet wirecheck --protocol diameter --hex 010000148000013e010000230000000100000002
```

Для файла: `python -m hetnet wirecheck --protocol sip --input /path/to/local-message.bin`. Никаких сетевых интерфейсов, PCAP sniffing или передачи сообщений нет. Успешный разбор означает лишь корректную структуру выбранного **подмножества**, а не соответствие сервера или сети стандартам.

## 2. Калибровка нагрузки по агрегированным записям

Формат входных данных — JSON с массивом `measurements`; каждая запись имеет **ровно три** ключа: `domain`, `duration_seconds`, `request_count`. Домен — один из `map_2g`, `map_3g`, `diameter_4g`, `sip_ims`, `sbi_5g`. Подписанные `request_count` — это внешние входящие **инициирующие запросы**, не сумма запросов и ответов в журнале.

```bash
python -m hetnet calibrate --input examples/synthetic_aggregate_counts.json --output results/calibration.json
python -m hetnet run --duration 120 --subscribers 16 --seed 42 --traffic-profile results/calibration.json --output results/calibrated-run
```

Скорость определяется **взвешенно по времени**: `sum(request_count) / sum(duration_seconds)` для каждого домена. Отсутствующие домены используют демонстрационные базовые интенсивности. Не нужно подавать IMSI, SUPI, телефонные номера, сигнальные payload или другие персональные поля. Пример из репозитория — **вымышленные**, а не операторские данные. Суточная амплитуда и AR(1) **не извлекаются** из одной агрегированной величины и остаются синтетическими параметрами, как и в предыдущем этапе.

## 3. Разделение обучения и теста, две гранулярности метрик

```bash
python -m hetnet validate --duration 18 --subscribers 8 \
  --train-start-seed 21 --train-runs 5 \
  --test-start-seed 42 --test-runs 10 \
  --traffic-profile results/calibration.json --output results/validation
```

- На обучающих seed **21–25** симулируется только нормальный трафик. Отдельный `OfflineDetector` использует роли/разрешённые операции и максимальное число `SIP.INVITE` за скользящую секунду на чистых прогонах. Порог равен max(6, 99-му перцентилю максимумов чистых прогонов).
- На тестовых seed **42–51** инжектируются синтетические эпизоды. Детектор читает только `time_ms`, `source`, `target`, `operation`, `correlation_id`; **не** читает поле `attack` и уже сформированные тревоги. Встроенный детектор сравнивается как самостоятельный baseline.
- Для **эпизодов** объединяются атакующие *начальные* запросы, относящиеся к одному источнику, протоколу и псевдоабоненту, при межсобытийном разрыве до 1000 мс. Одна тревога, попавшая в любое событие эпизода по `correlation_id`, обнаруживает эпизод **один раз**. Легитимные корреляции остаются отдельными отрицательными примерами.
- Автоматически порождённые SIP ACK/BYE и ответы не образуют дополнительных эпизодов; атаки на КИЕ/профиль узла **не включаются** в эту метрику и требуют отдельной оценки на уровне узла.
- Тестовые результаты дополнены независимыми **чистыми контрольными прогонами**. Важно сравнивать с прежней метрикой Stage 2: там каждая корреляция SIP-флуда считалась отдельно, что давало меньшую recall. В Stage 3 метрика **другая**: не улучшение того же классификатора и не показатель обнаружения всех пакетов.

Сравнение строится на одних и тех же штатных и атакующих *сценариях симулятора*. Даже при полном совпадении метрик это **не** внешняя независимая проверка с данными оператора.

## 4. Стресс без атак — проверка ложных тревог

```bash
python -m hetnet stress --duration 18 --subscribers 8 --test-runs 3 \
  --scales 1,8,20 --loss-rates 0,0.1 \
  --traffic-profile results/calibration.json --output results/stress
```

Каждый стресс-прогон имеет `inject_attacks=False`. Оцениваются только **ложные тревоги (FPR)** и связность с состояниями потери/перегрузки: у чистого набора нельзя содержательно определять recall/precision. Обучение offline-detector выполняется однократно на номинальном нормальном трафике с другими seed и не подстраивается к тестовым условиям.

Сильные потери могут приводить к каскаду просроченных ответов и ложных тревог встроенного детектора; отсутствие тревог у отдельного offline-detector не доказывает его превосходства: у него **меньше типов проверяемых инвариантов**.

## 5. Статус соответствия

Реализованы ограниченные офлайн-валидации **формата**, некоторые логические инварианты 2G–5G и воспроизводимые synthetic experiments. **Не выполнены** полные conformance/interoperability испытания TS 29.xxx, тесты TCAP/ASN.1, проверка NSSAI/QoS, NF security/SEPP/OAuth2, действительный HTTP/2 SBI, 5G NR radio, реальные N26/S3 handover. **Не измерены** промышленная обнаружительная способность, AUC-ROC/PR, статистическая значимость против других ML подходов. Все ограничения должны сохраняться при публикации результатов.
