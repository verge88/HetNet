# Этап 13 HetNet — долговременная защита от повторов и отзыв ключей

## Назначение и ограничения

На этапе 12 проверка HMAC была привязана к локально доверенным
key_id, source_id и lineage_id, но защита от повторной подачи
заканчивалась при завершении процесса. Этап 13 добавляет SQLite
с долговременным максимальным sequence для каждого key_id и
необратимым в прикладном API статусом revoked.

Это исследовательская лабораторная модель для обезличенных
агрегатов, а не промышленная система PKI/HSM и не полное
соответствие требованиям сетей 2G–5G/3GPP.

## Хранимые сведения

В приватной SQLite-базе фиксируются key_id, source_id,
lineage_id, SHA-256 отпечаток высокоэнтропийного HMAC-ключа,
последний принятый sequence и флаг revoked. Исходный секрет,
операторские сигнальные сообщения, полные счётчики и экспертные
аннотации в БД не записываются.

Требования на POSIX: приватный каталог 0700, файл SQLite
0600, никаких symlink и hardlink. Создание базы производится
отдельной явной командой, не при попытке первого импорта.
SQLite открывается в режиме read-write без права автоматически
создавать отсутствующий файл. Если база была удалена, проверка
завершается ошибкой. При попытке инициализировать существующую
базу программа также отвечает отказом.

Перед обновлением состояния проводятся HMAC-верификация ВСЕХ
входов, проверка обязательных clean-only train, разделения
источников и lineages. Счётчики обновляются только затем,
в одной транзакции BEGIN IMMEDIATE. При отказе из-за одного
ключа откатываются изменения всей партии. Второй процесс
не сможет одновременно принять уже закреплённый sequence
для того же ключа.

## Практический локальный запуск

Сначала администратор создаёт приватный каталог:

    install -d -m 700 /private/hetnet-state

    python -m hetnet attestation-init-state \
      --state-db /private/hetnet-state/anti-replay.sqlite3

Проверка ранее созданных, подписанных и разрешённых агрегатов:

    python -m hetnet durable-attested-eval \
      --train /private/data/clean-a.envelope.json \
              /private/data/clean-b.envelope.json \
      --holdout /private/data/episode-a.envelope.json \
      --trust-config /private/keys/hetnet-trust.json \
      --state-db /private/hetnet-state/anti-replay.sqlite3 \
      --output /private/reports/episode-evaluation

Файл политики доверенных ключей, описанный на этапе 12,
содержит явные соответствия key_id, source_id, lineage_id
и секретов HMAC. Он хранится вне репозитория, в режиме 0600.

Статус:

    python -m hetnet attestation-state \
      --state-db /private/hetnet-state/anti-replay.sqlite3

Отзыв уже принятого key_id:

    python -m hetnet attestation-revoke \
      --state-db /private/hetnet-state/anti-replay.sqlite3 \
      --key-id sensor_lab_one

При отзыве даже корректно подписанные новые сообщения
от старого key_id перестают приниматься. При смене ключа
нужно создать НОВЫЙ key_id и новый секрет, заменить старую
привязку в локальной политике, после чего начать собственную
монотонную последовательность с 1. Старый отозванный
key_id остаётся в SQLite. Повторная привязка того же key_id
к другому секрету, source_id или lineage_id запрещена.

## Транзакции, повторы и аварии

Проверяющая программа сначала вычисляет отчёт Stage 11/12
по криптографически проверенным входам, а потом закрепляет
номер последовательности в SQLite. Выходной JSON записывается
уже после успешного commit. Если запись отчёта после commit
не удалась, те же signed-envelope повторно не принимаются:
это семантика at-most-once, а НЕ exactly-once между SQLite
и файловым экспортом. Безопасный механизм повторного экспорта
уже подтверждённого отчёта ещё не реализован.

Повторное использование старых ПОДПИСАННЫХ обучающих файлов
с прежними sequence также блокируется. Повторное подписание
старых данных с новым sequence не доказывает их свежесть.
Для повторно используемого обучающего эталона понадобится
отдельная модель trusted pinned snapshot.

Если SQLite удалена, импорт останавливается. Однако
злоумышленник с доступом на запись к базе может
восстановить устаревший backup или вручную изменить
содержимое. Приложение не защищено от такого отката
БЕЗ отдельного внешнего защищённого монотонного журнала.
Это серьёзное ограничение долговременной защиты.

## Синтетическая воспроизводимая демонстрация

    python -m hetnet durable-replay-demo \
      --output results/stage13/durable-demo

Программа создаёт пять синтетических агрегатов и случайные
HMAC-ключи в памяти. Временная приватная SQLite база
инициализируется, открывается повторно и показывает:

1. Приём первой партии из пяти подлинных для данного ключа файлов.
2. Отклонение точного повтора после нового открытия SQLite.
3. Отзыв одного key_id и отклонение его новой корректной подписи.
4. Принятие файлов после создания нового key_id и нового секрета.
5. Сохранение отозванного статуса старого идентификатора.

Временная база и все секреты уничтожаются при выходе.
В артефакте — только сводные метрики, псевдонимы и статусы.
Демонстрация НЕ подтверждает внешнее физическое происхождение
или достоверность измерений.

## Что НЕ подтверждено

- Хранение SQLite без защищённого TPM/HSM и независимого
  монотонного журнала не обеспечивает защиту от
  умышленного отката файла или его резервной копии.
- HMAC подтверждает утверждение держателя локально
  доверенного секрета, не качество измерений, не
  правомерность сбора и не честность экспертной разметки.
- Никаких разрешённых операторских источников или
  физически независимых датчиков пока не подключено.
- Все тестовые данные синтетические. Соответствие
  полному 3GPP Release 18/ITU-T wire stack не проверено.
