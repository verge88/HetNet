**Источник проверяемых результатов:** [GitHub Actions, run 44302651182](https://github.com/verge88/HetNet/actions/runs/44302651182); архив артефакта `hetnet-stage3-episode-validation` содержит `traffic_profile.json`, `validation.json`, `stress.json`. Тестирование выполнено на Python 3.10 и 3.12, **40 unittest tests passed**.

## 1. Synthetic benchmark: группировка атак по эпизодам

Сценарий: 18 с, 8 абонентов, `seed 21–25` — чистая обучающая выборка, `seed 42–51` — отложенные тестовые прогоны. Скорости фона взяты из **вымышленного** файла `examples/synthetic_aggregate_counts.json`, а не с работающей сети. В чистых контрольных прогонах — 403 отрицательных корреляции по 10 seed.

| Показатель, **эпизодный уровень** | Built-in monitor, mean | Offline rule/quantile baseline, mean |
|---|---:|---:|
| Precision | 1,000 | 1,000 |
| Recall | 1,000 | 1,000 |
| F1 | 1,000 | 1,000 |
| FPR | 0,000 | 0,000 |
| Ложные срабатывания на штатных контрольных прогонах | 0/403 | 0/403 |

Выборочное СКО каждого показателя равно 0 для десяти идентичных по структуре сценариев. Четыре положительных эпизода в каждом тестовом прогоне — три запроса от запрещённого источника в разных сигнальных стеках и один SIP-флуд, образованный 14 запросами. **Нельзя интерпретировать Precision/Recall=100 % как подтверждение эффективности на иных сетях/атаках**: данные специально построены вокруг узких правил детектирования.

Показатель Stage 2 `recall = 0,2353` относился к **корреляции каждого сообщения отдельно**: одна тревога SIP-флуда сопоставлялась лишь с одним из четырнадцати связанных запросов. Метрика Stage 3 отражает лишь обнаружение факта кампании, а не количество её сообщений. Соответственно метрики **не сравнимы напрямую**.

## 2. Обнаруженный эффект: FPR при безвредных потерях

Выполнено 18 **чистых** стресс-прогонов (3 seed × 3 интенсивности × 2 вероятности потерь) на 18 с с оценкой двух детекторов. Ни в одном из стресс-прогонов нет искусственных атак. Показаны средние доли корреляций с ложными тревогами по 3 seed:

| Scale | Loss на hop | Встроенный FPR | Offline FPR | FP встроенного / negative correlations, суммарно |
|---:|---:|---:|---:|---:|
| 1 | 0,00 | 0,000 | 0,000 | 0 / 123 |
| 1 | 0,10 | 0,347 | 0,000 | 42 / 123 |
| 8 | 0,00 | 0,000 | 0,000 | 0 / 470 |
| 8 | 0,10 | 0,164 | 0,000 | 77 / 470 |
| 20 | 0,00 | 0,000 | 0,000 | 0 / 1090 |
| 20 | 0,10 | 0,135 | 0,000 | 148 / 1090 |

Отдельный baseline не генерирует тревоги на потери/тайм-ауты и не проверяет многие инварианты, поэтому **нулевой FPR не означает более высокую полноту или качество**. У встроенного baseline значительная часть безвредных просрочек при 10%-ных потерях на каждом hop интерпретируется как аномалия. При этом выражение `loss_rate=0.1` относится к каждому направленному переходу, а не к 10%-ной потере сквозного сообщения. Наблюдаемые доли — только значения созданной модельной нагрузки и выбранного размера окна/таймера.

**Инженерный вывод**: требуется разделять security incidents и последствия обычной деградации канала, оценивать базовые транспортные потери при тревоге, добавить пороги неопределённости, корреляцию по маршруту/перегрузке и калибровку по чистым сценариям с потерями, не допуская уменьшения обнаружения скрытной компрометации КИЕ.

## 3. Офлайн-протокольные тесты

Пройдены положительные и отрицательные тесты envelope-подмножеств:
- Diameter v1, application-ID/command code, vendor AVP, длина AVP и padding.
- GTPv2-C TEID и Sequence, IE length, неверная версия/обрезка и отклонение piggyback как неподдерживаемого.
- SIP request/response line, Call-ID, CSeq, обязательные поля, byte Content-Length, отказ для неверной структуры.
- HTTP/2 фиксированный заголовок, SETTINGS/PING, длина и stream ID.
- Входные ограничения 1 МиБ и CLI hex.

Эти тесты **не** проверяют совместимость с независимыми промышленными реализациями и не означают полного покрытия RFC/3GPP.

## 4. Ограничения / обязательный следующий этап

1. Получить независимые *разрешённые и обезличенные* агрегаты действительной нагрузки; раздельно оценить интенсивность, суточный профиль, AR-коэффициент и периоды отказов. Текущий входной файл демонстрационный.
2. Сформировать наборы атак с независимыми источниками и разными профилями/уровнями изощрённости, а также базу нормальных сетевых отказов; держать источник сценариев раздельно от алгоритмов оценки.
3. Реализовать полноценные сессионные слои SIP/IMS и Diameter AVP typing, ASN.1/TCAP MAP, GTP IE vocabularies и 5G SBI OpenAPI/HTTP2, выполнить interop тесты по точным редакциям спецификаций. По состоянию этапа 3 соответствие wire-level **не подтверждено**.
4. Контролировать изменение FPR на стрессах и отдельно измерять безопасность КИЕ и проверки NFProfile; не смешивать с положительными эпизодами сообщений.
