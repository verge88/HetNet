# Этап 12 HetNet — аттестация агрегатов и ошибки временной привязки

## 1. Границы реализации

HetNet остаётся исследовательской синтетической моделью контроля КИЕ,
сопоставляющей логические узлы 2G/3G/4G/IMS/5G. До этого этапа входные
агрегаты содержали исключительно **заявленные** признаки корректности
контроля; никакая подлинность поставщика не проверялась.

В Stage 12 добавлены два независимых исследовательских инструмента:

1. **Криптографическая целостность и источник утверждения** —
   HMAC-SHA256 от всего канонического агрегированного объекта,
   включая точные отчётные значения и *эпизодную разметку*,
   с явным локальным связыванием key_id, source_id и lineage_id.
2. **Чувствительность временного обнаружения** к фиксированным
   смещениям дискретных временных интервалов для разных
   контролируемых узлов; метки эпизодов и обученные пороги
   остаются неизменными.

**HMAC не доказывает физическое происхождение измерения.**
Он лишь проверяет, что носитель локально доверенного секрета
мог подписать конкретное утверждение. Доверенная ключевая политика
и её организация необходимы вне симулятора. Самоподписание
синтетического файла случайным ключом не превращает его в
независимое измерение и не подтверждает добросовестность экспертной
разметки. Не реализованы HSM, PKI, взаимная аттестация устройств,
отзыв ключей, внешняя доверенная временная метка,
операторская маршрутизация или реальный перехват сигнализации.

## 2. Экспериментальный envelope v1

Один локальный JSON envelope содержит **ровно**:

| Поле | Содержание |
|---|---|
| envelope_version | Целое число 1 |
| key_id | ASCII-псевдоним доверенного ключа |
| sequence | Целое положительное 1…(2^53−1) |
| dataset | Полный локально валидируемый агрегат Stage 10 v1 или Stage 11 v2 |
| mac_sha256 | 64 шестнадцатеричных символа HMAC |

MAC вычисляется **с отдельным domain separator**:

    HMAC_SHA256(secret,
      b"HetNet/laboratory-aggregate-envelope/v1\\0" +
      canonical_json({
        envelope_version: 1, key_id, sequence, dataset
      }))

Канонизация выполняется стандартной библиотекой Python JSON:
сортировка ключей, компактные разделители, ASCII-экранирование,
запрет NaN/Infinity. До вычисления подписи выполняется строгая
валидация агрегата, включая форму узловых/временных меток.

Проверяющий **не принимает произвольный HMAC-ключ от отправителя**.
Он читает локальную политику, где указан разрешённый key_id и
**точная пара** source_id/lineage_id. При несовпадении,
неизвестном ключе, плохом MAC, некорректном JSON, добавленных
полях или неверной версии — **отказ до анализа метрик**.

Для сопоставления MAC используется \`hmac.compare_digest\`.
Проверка подписи распространяется на всю разметку,
но **не делает размеченное событие истинным**.

### Локальная политика доверия

Формат \`trust_config.json\`:

    {
      "schema_version": 1,
      "identities": [
        {
          "key_id": "sensor_lab_a",
          "source_id": "aggregate_source_a",
          "lineage_id": "capture_lineage_a",
          "secret_b64": "<приватный 32…64-байтный ключ в base64>"
        }
      ]
    }

Этот пример — **описание формата**, а не действительный ключ.
Файл должен находиться **вне git**, с доступом только
владельцу (0600 или строже на POSIX). Парсер отклоняет
повторные key_id, одинаковые байты ключей для двух
источников, дубли идентичностей, невалидный base64,
слишком короткие ключи и дополнительные поля.
Ключи не включаются в экспортируемый JSON, CLI-логи
или демонстрационные GitHub Actions артефакты.

Исследовательский CLI предполагает наличие уже
подписанных envelope-файлов и доверенного локального
trust-config. Нельзя считать секрет, созданный
отправителем и немедленно предложенный вместе
с файлом, независимым подтверждением его личности.
Не добавляйте реальные секреты и операторские
агрегаты в публичный GitHub или Actions.

### Повторы и возраст

\`ReplayGuard\` принимает строго возрастающие
\`sequence\` **по key_id** и отклоняет повторы и
устаревшие номера в *одном* процессе/батче.
Неверный MAC не расходует последовательность.

**Ограничение:** это память процесса. После
его перезапуска журнал пропадает; отсутствует
защита от повторного воспроизведения между
запусками, сетевой антиреплей-обмен,
постоянное доверенное хранилище, atomic CAS
или срок действия подписанного события.
Это не реализация production replay prevention.

## 3. Запуск аттестованной оценки

При наличии **разрешённых и корректно подписанных**
локальных envelope-файлов:

    python -m hetnet attested-episode-eval \
      --train /private/data/clean_alpha.envelope.json \
              /private/data/clean_beta.envelope.json \
      --holdout /private/data/episodes_alpha.envelope.json \
                /private/data/episodes_beta.envelope.json \
      --trust-config /private/keys/hetnet-trust.json \
      --output /private/results/attested-episodes

Для обучения допускаются только **чистые** Stage 10 v1 агрегаты;
для проверки — Stage 11 v2 с относительными эпизодами.
Перед расчётом всех метрик проверяются **все** MAC; тестовые
метки не участвуют в подборе порога. Сохраняется
разделение source_id и lineage_id, а точные копии рядов
выявляются каноническим SHA-256, как на этапах 10–11.

Экспорт \`attested_episode_comparison.json\`
содержит агрегированные эпизодные метрики,
верифицированные key_id, sequence и fingerprint
без сырых измерений, разметки по узлам и секрета.

### Воспроизводимая демонстрация без постоянных ключей

    python -m hetnet attestation-demo \
      --output results/stage12/attestation-demo

В этом режиме **программа сама генерирует**
одноразовые 32-байтные ключи в памяти, подписывает
пять явно синтетических файлов (2 train + 3 test)
и затем заново проверяет созданные MAC. Ни ключи,
ни подписанные файлы не записываются на диск или
в CI-артефакт. Выход явно содержит
\`self_signed_synthetic_demo: true\`.
Это проверка механики HMAC, **не внешняя аттестация**.

## 4. Смещения относительных временных интервалов

Stage 11 определяет тревогу по двум последовательным
интервалам наблюдения. В реальной системе
несогласованность часов или задержка датчика
может изменить сопоставимость этих интервалов.
Здесь исследуется только **одна упрощённая
компонента** этой проблемы — фиксированный сдвиг
целого номера относительного интервала
по каждому узлу (не более ±2).

В \`shift_interval_bins\` разрешено изменять
**только** \`interval_index\` строк, счётчики,
флаги подлинности и разметка эпизодов
не изменяются. Смещённые измерения за пределами
исходного временного окна исключаются, а потери
показываются явно. Исходный объект остаётся
неизменным.

Четыре предзаданных сценария:

| case | Сдвиги узлов (в бинах) |
|---|---|
| aligned | Все 0 |
| opposing_one_bin | msc2 +1, amf5 −1, sgsn3 +1, pcscf −1 |
| opposing_two_bins | msc2 +2, amf5 −2, sgsn3 +2, pcscf −2 |
| epc_ims_one_bin | mme4 +1, dra −1, pcscf +1 |

Одни и те же **два чистых тренировочных** источника
используются в каждой серии — порог не адаптируется
к тестовому смещению. Одни и те же три синтетических
эпизодных источника повторно оцениваются во
всех четырёх сценариях. Они являются **парными
трансформациями одного и того же набора**, а
не двенадцатью физически независимыми площадками.

    python -m hetnet clock-study \
      --train examples/labeled/lab_clean_alpha.json \
              examples/labeled/lab_clean_beta.json \
      --holdout examples/episodic/episodic_holdout_alpha.json \
                examples/episodic/episodic_holdout_beta.json \
                examples/episodic/episodic_holdout_gamma.json \
      --output results/stage12/clock-study

Экспорт \`clock_study.json\` содержит по каждому
сценарию number dropped/retained rows,
доступность проверяемых двухинтервальных пар,
episode recall, точность и задержки тревог.
Относительные **бины не являются миллисекундами**;
это не реальная модель PTP/NTP, jitter,
packet reorder, NTP holdover, LTE/NR time sync
или conformance 3GPP/ITU-T/IETF.

## 5. Принципиальные ограничения

- Настоящих измерений, физических независимых
  датчиков и внешне проверенной аннотации пока
  **нет**. Все демофайлы синтетические.
- HMAC подтверждает источник *утверждения*,
  не правдивость отчёта и не права на его передачу.
  Для production нужен независимый secure key
  provisioning, проверка пользователя/устройства,
  долговременная anti-replay state и аудит доступа.
- Подписанные булевы \`cu_verified_claim\` и
  \`quorum_verified_claim\` остаются **утверждениями**
  подписанта, не новой отдельной проверкой
  исходных индивидуальных CU/HMAC.
- Нормированные остатки и peer-медиана — правила
  симуляции, не сертифицированный ML,
  а результаты диссертации не воспроизводились.
- Нет полного wire-level соответствия
  стандартам 3GPP Release 18, ITU-T SS7/TCAP,
  Diameter/SIP, GTPv2-C, 5G SBI/HTTP2 или
  настоящей радиообработке GSM/UMTS/LTE/NR.
