# HetNet: единый симулятор сигнализации мобильных сетей 2G–5G

Исследовательский **дискретно-событийный симулятор**, в котором одновременно работают логические подсистемы 2G/3G (SS7/MAP), 4G EPC (Diameter + GTPv2-C), IMS (SIP) и 5G Core (SBI/HTTP/2). Объединяет топологию, часы, абонентов, межпоколенные переходы, унифицированный журнал событий, независимое наблюдение за сигнализацией и детекторы аномалий.

> **Границы соответствия:** набор операций, ролей и протокольных зависимостей согласован с указанными 3GPP/ITU-T/IETF спецификациями на уровне модели. Это **не** реализация полного стека GSM/UMTS/LTE/NR, не передача реальных сигнальных пакетов и не сертифицированное подтверждение соответствия 3GPP. Область охвата и исключения — в [матрице стандартов](docs/standards.md).

## Запуск

Нужен Python 3.10+; для модели и тестов нет сторонних runtime-зависимостей.

```bash
python -m pip install -e .
python -m hetnet run --duration 18 --subscribers 8 --seed 42 --output results
python -m hetnet serve --host 127.0.0.1 --port 8080
```

Откройте http://127.0.0.1:8080 — браузерная панель покажет топологию, счётчики, события, тревоги и позволит запустить новое моделирование. Веб-сервер слушает локальный адрес по умолчанию.

Параметры CLI: `--duration` (секунды), `--subscribers` (не меньше 4), `--seed` (воспроизводимость), `--loss-rate` (вероятность потери на каждом ребре), `--cu-interval` (мс), `--no-attacks` (только штатные процедуры). Команда `python -m hetnet standards` выводит сопоставление операций со спецификациями.

После прогона папка `results/` содержит `result.json`, `summary.json`, `alerts.json`, `topology.json` и `events.csv`. Поле `subject` использует **синтетические псевдонимы**, а не настоящие IMSI/SUPI.

## Что моделируется

- **2G**: MSC/VLR–STP–HLR, процедуры MAP SendAuthenticationInfo и UpdateLocation.
- **3G**: SGSN–STP–HLR, процедуры MAP SendAuthenticationInfo и UpdateGprsLocation (пакетная подсистема).
- **4G**: MME–DRA–HSS, Diameter AIR/AIA и ULR/ULA; MME–SGW, GTPv2-C CreateSessionRequest/Response.
- **IMS**: P-CSCF–S-CSCF, SIP REGISTER, INVITE, 1xx/2xx, ACK и BYE с корреляцией диалога.
- **5G**: gNB/AMF, AUSF, UDM, SMF, NRF, UPF и SEPP; логические запросы 5G SBA к сервисам NFDiscovery, UEAuthentication, UECM, PDU Session, NFManagement.
- **Совместная работа**: перемещение синтетического абонента 2G→3G, 3G→4G, 4G→5G либо 5G→4G; IWF регистрирует межпоколенное **семантическое** событие, после чего выполняется стандартная процедура в целевом поколении. Прямой MAP→SBI wire-трансляции не заявляется.
- **Безопасность и мониторинг**: разграничение операций по ролям, контроль NFProfile, скользящее окно SIP INVITE, SIP ACK-инвариант, контрольные информационные единицы (КИЕ) с HMAC и независимым сравнением счётчиков. Инъекции атак безопасно локальны и не взаимодействуют с реальными сетями.

Схема исследования взята из приложенной диссертации: разделы 3.2–3.8 (отдельные генераторы MAP/Diameter/SIP, общий формат события, КИЕ, инварианты, проверка воспроизводимости) и раздел 2.5 (5G SBA). Это **новая объединённая минимальная реализация**, а не воспроизведение всех моделей, параметров, результатов и ML-классификаторов диссертации.

## Проверка

```bash
python -m unittest discover -s tests -v
```

Тесты проверяют совместное присутствие поколений и стеков, детерминизм, межпоколенные события, корректность SIP ACK, валидацию NFProfile, нарушения политик, КИЕ, потери звеньев и экспорт результатов.

## Следующие этапы для расширенного нормативного соответствия

Для испытаний на уровне реального протокола потребуются отдельные ASN.1 BER кодеки MAP/TCAP/SCCP, Diameter AVP и транспорт (SCTP/TLS/IPsec), SIP transaction timers/IMS AKA, полноценный GTPv2-C, NGAP/NAS/RRC и 5G SBI JSON/OpenAPI/HTTP/2 с TLS/OAuth2/SEPP/N32, а также проверка конкретных версий 3GPP Release и TTCN-3/interop тесты. Такие функции **не** реализованы и не имитируются как будто они проверены.

## Этап 2 — расширенная имитация и научная воспроизводимость

- Пер-узловые потоки в пяти сигнальных доменах с суточной гармоникой, AR(1), семплированием Пуассона и контролем интенсивности через `--traffic-scale`.
- Ограниченная пропускная способность и буферы звеньев, причинная обработка пакетов hop-by-hop, задержки и состояния `CONGESTED`/ `LOST`.
- Состояния процедур 2G/3G, LTE, IMS и 5G с обязательными предшественниками, сопоставлением ответов и тайм-аутами.
- Агрегированные `observations.csv` по окнам ОКС-7 30 с, Diameter 15 с, SIP 20 с; GTP/5G — расширение.
- Экспериментальные серии seed 42–51 с отдельной оценкой message-level precision, recall, FPR, F1 и выборочного стандартного отклонения.
- Таблица конкретных редакций стандартов **3GPP Release 18**: [standards/release18.json](standards/release18.json).

```bash
python -m hetnet run --duration 60 --subscribers 16 --seed 42 --traffic-scale 2 --output results/run
python -m hetnet experiment --duration 18 --subscribers 8 --start-seed 42 --runs 10 --output results/experiment
python -m unittest discover -s tests -v
```

Полные допущения и ограничения: **[docs/validation-stage2.md](docs/validation-stage2.md)**. Генератор и его параметры являются новыми синтетическими допущениями: **это не** воспроизведение исходных 24-часовых наборов из диссертации и **не** сертифицированная протокольная реализация.

## Этап 3 — офлайн-проверка форматов и независимая оценка по эпизодам

Новые команды работают **только с локальными файлами или синтетическими событиями**. Никакие запросы в реальные мобильные сети не отправляются.

```bash
# Реальный бинарный envelope Diameter v1 (синтетические поля, без AVP)
python -m hetnet wirecheck --protocol diameter --hex 010000148000013e010000230000000100000002
# Калибровка по вымышленным агрегированным счётчикам
python -m hetnet calibrate --input examples/synthetic_aggregate_counts.json --output results/calibration.json
# Научная оценка по эпизодам: обучение на одних seed, тест на других
python -m hetnet validate --duration 18 --subscribers 8 --traffic-profile results/calibration.json --output results/stage3
# Только легитимные события: FPR при потере пакетов и росте нагрузки
python -m hetnet stress --duration 18 --subscribers 8 --traffic-profile results/calibration.json --output results/stress
```

Подробнее: [методика этапа 3](docs/validation-stage3.md) и [фактические результаты CI](docs/results-stage3.md). Валидаторы реализуют **ограниченный синтаксический слой** SIP, Diameter/AVP, GTPv2-C и HTTP/2; их принятие сообщения **не означает** полного соответствия RFC/3GPP или сетевой совместимости. Отсутствуют MAP/TCAP BER, реальная NGAP/NAS и 5G SBI/OpenAPI. Эксперимент на синтетических эпизодах специально отделён от метрик отдельных сообщений и от безопасности КИЕ.

## Этап 4 — доказательные признаки контроля КИЕ и потери

Симулятор отдельно отслеживает: (1) корректно подписанный, но не
соответствующий независимому учёту отчёт узла, (2) нарушение
подписи при изменении контрольного сообщения в пути и
(3) обычную потерю контрольного ответа. Выводы основаны на
отчётах CU.Reconciliation; событие потери само по себе не доказывает
компрометацию.

    python -m hetnet run --duration 18 --subscribers 8 --no-attacks --node-case report --output results/report-only
    python -m hetnet run --duration 18 --subscribers 8 --no-attacks --node-case tamper --output results/tamper-only
    python -m hetnet node-study --duration 18 --subscribers 8 --start-seed 42 --runs 6 --loss-rates 0,0.1,0.35 --output results/node-study

Экспорт: node_evidence.json и node_study.json. На веб-панели отображаются
свидетельства для каждого узла и доля доставки КИЕ.

**[Методика этапа 4](docs/validation-stage4.md)** /
**[Результаты эксперимента](docs/results-stage4.md)**.

КИЕ — исследовательский метод, не спецификация 3GPP. Различие
подписанного отчёта и независимого наблюдения остаётся подозрением,
а не доказательством взлома. Совместимость со стеком реального
оператора по-прежнему не заявляется.

## Этап 5 — наблюдатели из трёх независимых доменов

Для каждого опроса КИЕ моделируются три раздельно подписанных голоса наблюдения Legacy/EPC/5GC. Сравнение отчёта с независимыми счётчиками проводится только при проверенном большинстве **2 из 3**. Дубликаты, неверные подписи и устаревшие голоса не учитываются. Недостаток кворума означает **неопределённость**, а не доказательство взлома.

```bash
python -m hetnet run --duration 18 --subscribers 8 --no-attacks --node-case none --observer-case one_faulty --output results/observer-single
python -m hetnet run --duration 18 --subscribers 8 --no-attacks --node-case report --observer-case two_colluding --output results/collusion
python -m hetnet zone-study --duration 18 --subscribers 8 --runs 6 --observer-loss-rates 0,0.2,0.45 --output results/zone-study
```

Сценарии `--observer-case`: `none`, `one_faulty`, `two_colluding`, `outage`, `mixed`, `bad_mac`, `stale`. В `run` доступен параметр `--observer-loss-rate` (0…1). Веб-панель показывает доступность кворума, отклонённые/отсутствующие голоса и несогласное меньшинство; `node_evidence.json` и `zone_study.json` пригодны для повторной обработки.

**[Методика 5-го этапа](docs/validation-stage5.md)** · **[Результаты и ограничения](docs/results-stage5.md)**.

**Важно:** при сговоре двух из трёх наблюдателей большинство может обвинить честный узел и пропустить подделку. Это демонстрируемое ограничение модели, а не успешно отражённая атака. Административные домены и подписи — синтетические исследовательские конструкции, а не стандартный механизм 3GPP.


## Этап 6 — несколько сетевых поколений и коррелированные сбои наблюдения

Теперь можно одновременно подделывать отчёты контрольных узлов 2G,
3G, 4G, IMS и 5G, а также моделировать **общий** (не независимый
по узлам) сбой одного или нескольких административных доменов
наблюдения в одном периоде КИЕ.

    # Пример: подделка отчётов MSC (2G) и AMF (5G) при отказе 2 зон
    python -m hetnet run --duration 18 --subscribers 8 \
      --no-attacks --node-case none --report-fault-nodes msc2,amf5 \
      --shared-zone-case epc_5gc_outage \
      --output results/stage6/demo

    # 90 воспроизводимых прогонов: 6 seed × 5 режимов × 3 группы узлов
    python -m hetnet cohort-study --duration 18 --subscribers 8 \
      --start-seed 42 --runs 6 \
      --fault-cases none,epc_outage,epc_5gc_outage,epc_corrupt,epc_5gc_collude \
      --cohorts none,legacy_5g,epc_ims \
      --output results/stage6/cohorts

Новые результаты включают domain_evidence.json (общие
потери голосов, общие нарушения и недоступность кворума),
node_evidence.json и cohort_study.json. В веб-панели доступны
настройки нескольких узлов, общего сбоя зоны, его вероятности и
просмотр коррелированных событий.

**[Методика шестого этапа](docs/validation-stage6.md)** ·
**[Результаты 90 прогонов](docs/results-stage6.md)**.

**Ограничение:** логически разделённые наблюдатели пока получают
один общий *синтетический* транзитный счётчик. Это не три
независимых физических источника. Если два датчика в сговоре,
кворум 2/3 может скрыть подделку и обвинить честный узел;
общая потеря двух доменов означает неопределённость, а не
доказательство компрометации. Это не 3GPP conformance test.


## Этап 7 — статистика зон КИЕ и ошибки виртуальных наблюдателей

На основе зональной постановки диссертации (§3.3.3–3.4.5)
добавлены описательные признаки по подписанным и заново
проверенным КИЕ: медиана, z-score, MAD, ранги, leave-one-out
отклонения узлов 2G/3G/4G/IMS/5G. Нет достоверного
кворума или подписи — узел исключается из статистики,
а не считается нормальным.

Отдельно можно смоделировать **независимые случайные пропуски
событий виртуальными наблюдателями**, условно на одном
синтетическом потоке, и безопасно менять ограниченный
покомпонентный допуск согласованности подписанных векторов.
При неоднозначных кворумах вывод не принимается.

    python -m hetnet run --duration 18 --subscribers 8 \
      --no-attacks --node-case none --report-fault-nodes msc2,amf5 \
      --observer-capture-miss 0.05 --quorum-max-count-delta 2 \
      --output results/stage7/demo

    python -m hetnet probe-study --duration 18 --subscribers 8 \
      --start-seed 42 --runs 6 \
      --capture-miss-rates 0,0.05,0.15 \
      --tolerances 0,1,2 --cohorts none,legacy_5g \
      --output results/stage7/probe-study

    python -m hetnet serve

Экспорт: zonal_evidence.json и probe_study.json. В веб-интерфейсе
доступны вероятность ошибок виртуального захвата, допуск
кворума, ранги и z-оценки контрольных узлов.

**[Методика этапа 7](docs/validation-stage7.md)** ·
**[Результаты 108 синтетических прогонов](docs/results-stage7.md)**.

**Ограничение:** датчики не являются независимыми физическими
источниками, ошибки лишь независимо семплируются. Зональные
признаки описательные, не обученный ML-детектор и не
сертификационные 3GPP/ITU-T conformance результаты. Нулевой
допуск по умолчанию сохраняет прежний строгий алгоритм.


## Этап 8 — безопасный импорт агрегированных данных с разделением источников

Добавлен **локальный, строго ограниченный** JSON-интерфейс
для исследовательских счётчиков наблюдений. Он принимает
только pseudonymous source_id, coarse node/observer/operation_class,
относительный интервал, эталонный и наблюдаемый агрегированный
объём событий; идентификаторы абонентов, raw packet payload,
IP-адреса и дополнительные поля отклоняются.

    # Проверка синтетического демонстрационного источника
    python -m hetnet aggregate-audit \
      --input examples/external/lab_training_alpha.json

    # Калибровать 3 виртуальных наблюдателя по двум источникам,
    # проверить MAE и смещение на третьем, без подгонки по holdout
    python -m hetnet external-eval \
      --train examples/external/lab_training_alpha.json \
              examples/external/lab_training_beta.json \
      --holdout examples/external/lab_holdout_gamma.json \
      --output results/stage8/external

**[Методика и формат](docs/validation-stage8.md)** ·
**[Результаты CI](docs/results-stage8.md)**.

**Научная честность:** имеющиеся файлы на 100% синтетические.
source_id не доказывает физическую независимость приборов,
reference_count берётся из предоставленного файла без
внешнего подтверждения. Без размеченных атак нельзя
вычислить precision, recall, FPR или ROC-AUC.
Экспортируемый external_eval.json не содержит исходные
ряды и используется только для оценки калибровки
агрегированной доли пропусков. Не публикуйте
настоящие операторские данные без согласованного
разрешения и обезличивания; минимальный объём 20
событий не равен k-анонимности. Это не формальная
сертификация 3GPP Release 18/ITU-T.


## Этап 9 — сравнение зональных правил с базовым контролем КИЕ

Реализованы два простых пороговых **зональных**
детектора ложных отчётов сетевых узлов:
по нормированному абсолютному остатку и
по отклонению от медианы других узлов.
Они сравниваются с существующим правилом
повторно проверенного подписанного CU-отчёта
на одинаковых синтетических примерах.

Пороги зональных методов вычисляются только
по **чистым обучающим** source-профилям с seed
21–24; оценка — на других синтетических
профилях и seed 42–45. В тест включены
сдвиг погрешности наблюдателя, потеря
кворума и сговор большинства. Два
последовательных проверенных КИЕ обязательны
для принятия решения. Недостаток данных —
отдельное состояние **abstention**, а не
правильно распознанная норма.

    python -m hetnet zonal-compare \
      --duration 18 --subscribers 8 \
      --train-start-seed 21 --train-runs 4 \
      --test-start-seed 42 --test-runs 4 \
      --output results/stage9/heldout

Экспорт: zonal_comparison.json, включая
покрытие, TP/FP/FN/TN только по принятым
решениям и консервативную полноту по всем
атакованным узлам (abstentions как пропуски).

**[Методика этапа 9](docs/validation-stage9.md)** ·
**[Результаты 48 синтетических прогонов](docs/results-stage9.md)**.

**Важно:** имена source-профилей и различие
seed не доказывают независимость физических
измерений. Настоящие операторские данные и
внешние метки атак не подключены. Три детектора
основаны на тех же КИЕ/наблюдателях; зональные
правила не являются обученным ML. Проверки
реального 2G–5G wire-conformance не проводились.


## Этап 10 — внешне размеченные агрегаты: разделение источников и lineage

Добавлена **локальная** строгая схема для обезличенных
агрегированных CU-счётчиков с отдельными *узловыми*
метками атак. Поддерживается проверка пересечений
обучающей и тестовой выборок не только по source_id,
но и по заявленному lineage_id, а также по
SHA-256 отпечаткам **точно одинаковых**
измерительных рядов. Эти проверки выявляют
простые копии/утечки, **не доказывают** физическую
независимость источников и достоверность разметки.

Три детектора оцениваются в одинаковых
полных размеченных временных окнах:
cu_claimed_baseline (отчётный CU-базис
**без криптографической проверки внешнего файла**),
zone_absolute и zone_peer. Пороги зональных
методов определяются только по чистому train.
Если нет двух подряд пригодных измерений,
выдаётся **abstention**; отдельно рассчитываются
coverage и полнота по всем атакованным
узлам, включая пропуски.

    # Аудит структуры строго обезличенных данных
    python -m hetnet labeled-audit \
      --input examples/labeled/lab_clean_alpha.json

    # Демонстрация train/holdout на 4 явно синтетических источниках
    python -m hetnet labeled-eval \
      --train examples/labeled/lab_clean_alpha.json \
              examples/labeled/lab_clean_beta.json \
      --holdout examples/labeled/lab_holdout_gamma.json \
                examples/labeled/lab_holdout_delta.json \
      --output results/stage10/labeled

## Этап 11 — атаки с неизвестным началом и завершением

Добавлена отдельная схема **schema_version=2** с
непересекающимися полуоткрытыми эпизодами
\`[start_interval,end_interval)\` для контролируемых
узлов 2G/3G/4G/IMS/5G. Входом причинного сканера
являются **только обезличенные агрегированные
счётчики**, не интервальная разметка, названия
источников или будущие наблюдения. Отдельный
оценщик сопоставляет тревоги с размеченными
эпизодами **после** выполнения детектора.

- Нужны два соседних интервала с доступной
  КИЕ и кворумом (здесь лишь заявленные
  \`cu_verified_claim\`/\`quorum_verified_claim\`).
- Оцениваются **episode recall**, доля
  несопоставленных тревог, средняя задержка
  в единицах относительных интервалов и
  покрытие верифицируемыми парами.
- Одноинтервальные атаки честно учитываются
  как слишком короткие для двойного подтверждения.
- Пороги \`zone_absolute\` и \`zone_peer\`
  обучаются лишь на чистых Stage 10 источниках,
  а Stage 11 контрольные наборы имеют другие
  source_id, lineage_id и буквальные
  отпечатки measurement rows.
- Экспорт содержит сводные показатели,
  **не** покадровую truth-разметку или
  исходные измерения.

    python -m hetnet episode-eval \
      --train examples/labeled/lab_clean_alpha.json \

## Этап 12 — HMAC-аттестация агрегатов и рассогласование временных интервалов

Добавлен отдельный исследовательский envelope с
HMAC-SHA256, который связывает полный агрегат
со всеми его аннотациями, \`key_id\` и
монотонным \`sequence\`. Проверяющий использует
явную локальную политику доверия: каждому
\`key_id\` сопоставляются **конкретные**
\`source_id\` и \`lineage_id\`, а файл приватных
ключей не должен попадать в репозиторий.
Неправильный MAC или источник вызывает отказ
**до** вычисления научных метрик.

    # Демонстрация: подписываются только СИНТЕТИЧЕСКИЕ
    # файлы, секреты создаются и хранятся лишь в памяти
    python -m hetnet attestation-demo \
      --output results/stage12/attestation-demo

    # Для уже локально подписанных агрегатов и доверенного
    # приватного JSON trust policy (0600):
    python -m hetnet attested-episode-eval \
      --train /private/clean_one.envelope.json \
              /private/clean_two.envelope.json \
      --holdout /private/episode_one.envelope.json \
      --trust-config /private/hetnet-trust.json \
      --output /private/results

Отдельный \`clock-study\` проверяет, как
смещение **номеров относительных интервалов**
на один/два шага между узлами 2G/3G/4G/IMS/5G
изменяет число обнаруженных эпизодов,
неподтверждённые тревоги, задержку
и доступное покрытие при **том же**
обученном пороге. Истинные размеченные
эпизоды не перемещаются.

    python -m hetnet clock-study \
      --train examples/labeled/lab_clean_alpha.json \
              examples/labeled/lab_clean_beta.json \
      --holdout examples/episodic/episodic_holdout_alpha.json \
                examples/episodic/episodic_holdout_beta.json \
                examples/episodic/episodic_holdout_gamma.json \
      --output results/stage12/clock-study

**[Методика и доверенная политика](docs/validation-stage12.md)** ·
**[Измеренные результаты](docs/results-stage12.md)**.

**Важно:** HMAC удостоверяет только утверждение
держателя уже доверенного ключа, **не**
физическую подлинность датчика,
независимость канала или правильность метки
атаки. Anti-replay существует только
в пределах процесса и не переживает
перезапуск. Самоподписанная демонстрация
не является внешней аттестацией.
Сдвиги происходят в **относительных
бинах**, не в миллисекундах сети.
Открытые эксперименты по-прежнему
синтетические, 3GPP/ITU-T conformance
не подтверждался.


## Этап 13 — долговременный anti-replay и отзыв аттестационных ключей

На этапе 12 защита подписанного агрегата от повтора
действовала лишь в текущем процессе. Добавлен
**локальный закрытый SQLite-журнал**, который
сохраняет наибольший sequence для key_id,
источник/lineage привязки, отпечаток ключа
и необратимое состояние отзыва. Для нескольких
подписанных входов используется одна атомарная
транзакция; ошибка в одном источнике откатывает
изменения всей партии.

    # СОЗДАТЬ ОДИН РАЗ защищённый каталог и пустую БД
    install -d -m 700 /private/hetnet-state
    python -m hetnet attestation-init-state \
      --state-db /private/hetnet-state/attest.sqlite3

    # Использовать локальные подписанные, разрешённые данные
    python -m hetnet durable-attested-eval \
      --train /private/data/train-one.envelope.json \
              /private/data/train-two.envelope.json \
      --holdout /private/data/test-one.envelope.json \
      --trust-config /private/keys/hetnet-trust.json \
      --state-db /private/hetnet-state/attest.sqlite3 \
      --output /private/results

    # Статус и отзыв существующего key ID
    python -m hetnet attestation-state \
      --state-db /private/hetnet-state/attest.sqlite3
    python -m hetnet attestation-revoke \
      --state-db /private/hetnet-state/attest.sqlite3 \
      --key-id sensor_lab_one

    # Безопасная лабораторная демонстрация
    # исключительно на синтетических данных
    python -m hetnet durable-replay-demo \
      --output results/stage13/durable-demo

В демонстрации одноразовые ключи генерируются
в памяти, а приватный файл SQLite создаётся
во временном каталоге и удаляется после
эксперимента. Показываются отказ в точном
повторе после повторного открытия БД,
долговременный отзыв и приём нового
ключа **только с новым key_id**. Никакие
приватные ключи и исходные строки агрегатов
не сохраняются в GitHub Actions артефакте.

**[Методика и порядок инициализации](docs/validation-stage13.md)** ·
**[Результаты проверок](docs/results-stage13.md)**.

**Ограничение:** база не имеет аппаратной защиты
от отката или подмены файла. Удаление базы
вызовет отказ импорта, но восстановление
устаревшего backup нельзя распознать без
независимого защищённого журнала. HMAC не
подтверждает правильность данных и
идентичность физических датчиков.
Все открытые испытания синтетические,
полный 3GPP Release 18 conformance не заявлен.
